# Group 6 — Billing review (in progress)

Reviewed against the admin Group 6 design on October 19, 2026. This is **not** a completion sign-off for Group 6.

The authenticated Billing page loads the seeded invoices, status filters, payment modal, new-invoice form, plans, child rate changes, bulk exports, and overdue-reminder controls. The overdue invoice modal was opened read-only; it exposes a payment amount and method. No real payment, invoice, void, or reminder was submitted during browser verification.

One shared ledger-safety gap is now closed. The admin payment RPC locks the invoice, accepts only an open/overdue unpaid balance, and rejects overpayment and repeat payments. Voiding an invoice with a settled payment is blocked at the database layer. The web screen calculates remaining balance from succeeded payments only, exposes payment for overdue records, and closes/refreshes after success. The iOS admin method value now matches the database's `etransfer` value while still displaying “E-transfer.” The migration was applied to the linked development project, and a rollback-only database test passed for partial payment, overpayment, settlement, duplicate payment, and void rules. Web lint, web/mobile typechecks, and the web production build passed.

Still outside the verified scope: annual per-child tax form generation and publication, mismatch-resolution workflow, payment-plan acceptance, autopay invites/payouts, and the full receipt/rates experience in the admin console. The current web screen explicitly labels autopay and payout as future Stripe work; the parent app has separate demo billing flows, but that does not establish end-to-end production payments. These areas need separate implementation and testing before Group 6 can be called complete.

The next read-only slice added Billing → Families and a household statement route. Admins can now open an active family, review its complete signed ledger with a running balance, compare that balance to unpaid invoice amounts, and drill into each invoice. The route checks the active center before showing a family. Ledger and family-invoice queries page deterministically rather than silently stopping at Supabase's default row limit. Browser checks with the seeded Ferreira and Castillo families confirmed links, payment/refund entries, invoice navigation and corrected date-only due dates; no ledger data was changed. This is an account view, **not** an annual tax statement or a published parent document. Those workflows remain open.

The parent app previously generated a downloadable “tax receipt” from the previous year's *family-wide* succeeded-payment sum. That figure was not child-specific, did not account correctly for refunds, and had no admin review or publication step. The unreviewed figure is now disabled in the linked development database and the parent app no longer offers its misleading PDF. Monthly statement sharing is unchanged. The parent app instead says an annual tuition statement has not been published. A seeded-parent RPC regression check and mobile typecheck passed. This is a safety correction, **not** implementation of 6c–6e: a per-child calculation, reconciliation/review, provider tax profile, versioned PDF publication and parent download flow still need to be built and verified before any annual document is released.

The family statement now includes a read-only payment-date review for the current and two prior years. It groups child-linked receipts and refunds, excludes non-CAD records from the displayed CAD figures, and flags unassigned payments and missing dates. Browser checks against the Castillo seed confirmed $13,980 received in 2025 and $3,600 received / $1,180 refunded in 2026. These are **recorded payment-activity figures only**; they are not tax-eligible amounts, and this section cannot publish a form. Web build, lint and web/database typechecks passed.

The next draft-only slice adds a private billing provider profile in Settings: legal business name, statement address, optional jurisdiction-specific registration/license details, and signer. Only admins with billing edit permission can read or change it. The saved registration identifier is masked in the UI and omitted from the audit record. The family payment-review page now flags missing provider details and links to Settings for editors; it does not imply that recorded details make a tax statement ready. The linked development migration was deployed, and a rollback-only database test confirmed an owner can write/read, a parent cannot read, and the test identifier does not appear in audit history. No actual provider registration identifier was entered. Eligibility, discrepancy resolution, approval, versioned PDF publication and parent access remain open.

The family payment-review page now also lists invoice lines attached to child-linked CAD payment or refund activity in the selected year. Billing editors can mark each line as a care-service *candidate*, excluded from a future draft, or still needing review, with a recorded reason. The database validates center/family ownership and the payment year; the review stores an invoice-line snapshot so later description or amount edits flag the decision as stale. Parents cannot read these internal classifications, and the audit record does not copy the private reason. A rollback-only owner/parent/year-mismatch test passed, and the seeded Castillo screen plus missing-reason validation were checked in the browser. Web lint, typecheck and production build passed. **No paid amount is allocated across lines yet**; classifying every line does not produce an eligible amount or make any document publishable. Refund reconciliation, service-period evidence, recipient details, approval, versioned PDF publication, and parent access still need separate work.

The next internal slice adds exact payment and full-refund allocation to the reviewed lines of each payment's own child-linked invoice. Editors must allocate an entire event, including excluded lines, before it is marked reconciled. The database locks the payment/invoice, verifies current line-review snapshots and the invoice total, rejects duplicate or foreign lines and over-allocation, and ensures a refund cannot exceed its original line allocation. It retains the allocation year, actor and audit event; only billing editors can read the allocation table, and only they can call the write function. The linked development migration was deployed. A rollback-only seeded-owner/parent test passed for exact allocation, over-allocation, invalid refund and parent isolation. The 2025 Castillo browser view correctly leaves the event locked until its line is reviewed; no actual line decision or allocation was saved. Web and database typechecks, web lint and production build passed. **This remains reconciliation evidence, not an eligible-expense total or a tax statement.** Service-period evidence, non-invoice credits, discrepancy resolution, final approval, a versioned PDF and parent publication remain open.

The invoice-line review now also captures care start/end dates and a note identifying their source. The database requires paired, chronological dates and at least eight characters of evidence whenever dates are entered. Care-service candidates without this evidence stay visibly incomplete; the payment date is not treated as the date of care. A separate family-review section lists manual household credits, adjustments and write-offs in the selected year as unresolved, even if an entry happens to reference an invoice, rather than silently assigning them to a child or subtracting them from allocated payments. The linked development migration and rollback-only validation/parent-isolation test passed. The browser displays the new fields and unresolved-adjustments section for the Castillo family, without saving real review data. **The source note is an admin assertion, not verification of an underlying document.** Assignment of these adjustments, cross-year service treatment, discrepancy resolution, approval and publication are still open.

The household-adjustment section now has an internal disposition form for CAD manual credits, write-offs and adjustments: still needing review, possibly related to one child-linked invoice line, not child care, or accounting follow-up. A possible line relationship is intentionally **not** a monetary allocation. The database validates the entry's center, family, currency and local review year, and permits a line reference only on an active child-linked invoice for that family (and on the entry's source invoice, if supplied). It snapshots the entry/line to flag later changes, keeps reasons out of the audit payload, and denies parent access. A rollback-only test created a temporary $25 credit, saved a possible relation, rejected a different family's line and wrong year, checked audit privacy and parent isolation, then rolled everything back. No persistent credit was created; the seeded Castillo browser page verifies the empty state only. Further accounting application and statement eligibility remain open.

An internal annual reconciliation checklist now collects the family's known operational gaps in one place: missing provider identity, undated/unassigned/non-CAD or unreviewable payment events, stale/unclassified lines, missing or cross-year care evidence, mismatched invoice totals, incomplete payment/refund allocations, and manual adjustments still needing resolution. Each item links to the relevant section. It never enables approval or publication, and a zero-issue state explicitly remains *not* a tax or accounting sign-off. Pure logic tests cover a clean data set, incomplete/stale evidence, cross-year care, no activity, excluded-only lines, undated/non-CAD records and inactive invoices. The seeded Castillo 2025 and 2026 browser pages displayed the expected three issue categories (provider details, line classification and payment allocations), with counts matching the underlying records. No database mutation was needed for this slice.

The next read-only slice adds an internal child-by-child worksheet beneath the household checklist. It keeps recorded receipts/refunds separate from net allocations to reviewed care-service candidate lines and excluded lines. Allocation subtotals are withheld if that child's reviewable events do not match recorded activity, an invoice or allocation is incomplete, a line decision is missing/stale, or care-date evidence is missing or falls outside the selected payment year. Household adjustments and unassigned records remain outside child subtotals. The worksheet explicitly does **not** represent eligibility, human approval, a tax total, or a parent document. Pure calculation tests cover exact receipt/refund splitting and each withholding condition; web typecheck, targeted lint and production build passed. The seeded Castillo page was opened in the local browser for both 2025 and 2026: it showed $13,980 received / $0 refunded and $3,600 received / $1,180 refunded respectively, with reviewed allocation values withheld pending classification and reconciliation. No review decisions or financial records were changed. A finalized eligibility policy, accounting resolution, approval, versioned PDF, publication and parent access remain open.

The Group 6f mismatch investigation now compares active CAD invoices **issued** in the selected year with child-linked receipts less refunds **recorded** in that year, then lists each contributing invoice with a source link. These are different accounting views; a difference is not automatically an error or a tax-statement amount. The comparison excludes void/draft and non-CAD invoices from billed totals and does not post a correction, choose a tax method, regenerate a document or notify a family. Pure tests cover cross-year settlement, next-year refunds and inactive/foreign records. In the local browser, the Castillo 2025 view matched $13,980 billed and paid; 2026 showed $3,660 billed against $2,420 net payment activity, with the $1,240 difference visibly tied to the unpaid August invoice. Web typecheck, targeted lint and production build passed. Actual accounting resolution and statement approval/publication remain separate unfinished work.

Billing editors can now record a private, per-invoice explanation for an annual invoice/payment timing difference: explained timing, explained open balance, or accounting follow-up. The database verifies the invoice, family, center, CAD currency and year, then snapshots the invoice and linked receipt/refund figures so a later change marks the explanation stale. The note is not copied into the audit payload, parents cannot read the review, and saving it does not alter a ledger entry or approve a statement. The migration was applied to the linked development project; a rollback-only test checked owner access, parent isolation, year validation, snapshot capture and audit privacy. In the local browser, the seeded Castillo 2026 page showed the $1,240 unpaid August invoice as unexplained and rejected a blank note without saving. The annual checklist now calls out missing, stale or follow-up timing reviews. Web typecheck, targeted lint and pure tests passed. No real invoice explanation was saved during verification. Accounting sign-off, statement approval, versioned publication and parent access remain open.

The next handoff adds an **admin-only, downloadable reconciliation evidence CSV** for a selected family and review year. It carries source invoices and lines, dated receipts/refunds (including missing-date exceptions), stored line decisions and care-date evidence, payment allocations, manual household adjustments and invoice/payment difference explanations. It marks missing or stale review snapshots, includes source IDs and review timestamps, and deliberately contains no tax-eligible or approved total. The download requires the billing edit permission and same-center family, is not cached, and writes a private audit event before the file is returned. The audit migration was applied to the linked development project and a rollback-only test checked owner audit creation, invalid-year rejection and parent denial. The unauthenticated local route redirects to sign-in; no family export was downloaded during verification. Web and database typechecks, targeted lint, pure export/reconciliation tests and the production build passed (the build warned that the installed Next.js 16.4.0 has a known security vulnerability; it should be upgraded separately). This is a review handoff, **not** approval, publication or a parent-facing document.

The private CSV now identifies its center and family by both name and stable ID, and includes a child ID beside each child-linked evidence row. This prevents two families or same-name children from becoming ambiguous when files are reviewed outside the app. It does not add provider registration details, approval, tax calculations or parent access.

The main Billing invoice query now loads every page in a stable issue-date/ID order instead of silently stopping at Supabase's default row cap. Dashboard no longer fetches the entire historical invoice list to show overdue reminders; it retrieves only the eligible invoice IDs in bounded batches. Local tests cover more than 1,000 invoices, an exact full page, a later-page failure, and multiple targeted batches. This removes a data-completeness gap but does not replace a live high-volume browser pass.
